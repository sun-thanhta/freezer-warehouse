## 2. ユーザーストーリー

倉庫管理者（manager）として、出荷前の全オーダーのうち、顧客が既に受け取ったロットより期限の早いロットしか残っていない行を一覧で事前に知りたい。なぜなら、出荷当日に日付逆転でブロックされてから気づくと、代替ロットの手配も例外の承認も間に合わず、配送が止まるからだ。

## 3. 背景・目的

- RFP の US-02 と BR-DATE-01 は、日付逆転を **出荷前に** 警告することを求めている。SQL だけで判定すると、作業者は確定ボタンを押すまで止まることを知らない（ADR-003 の不採用案 E）。
- 本ストーリーは日付逆転アラート画面（SCR-05、URL `/alerts`）の画面枠と、「ブロックされる出荷予定」「代替ロットで回避済み」の 2 ブロックを実装する。判定は E-05-S02 の共通エンジンを使い、引当画面・一覧・ダッシュボードと数値を一致させる。
- 判定の原則：基準は **同一顧客×SKU** に納品済みの最大期限。本日日付とは比較しない。他顧客の履歴は借用しない（CUS-005 が CHI-002 未受領なら、CUS-003 が新しいロットを受け取っていても古いロットを出荷できる）。

## 4. 対象ユーザー

| ロール | 本ストーリーでの利用 |
| --- | --- |
| manager（倉庫管理者） | 主利用者。シフト開始時に停止予定の行を把握し、代替ロット手配・例外承認の準備をする |
| warehouse（倉庫作業者） | 停止予定オーダーを開き、別ロットの選択または例外申請（E-06-S02）へ進む |
| qa（品質管理） | 閲覧のみ |
| sales（営業・CS） | 閲覧のみ。顧客へ事前に連絡（書面同意の取得など）する判断材料にする |
| admin / auditor | 閲覧のみ |

## 5. スコープ

**対象範囲**

- `/alerts` 画面の枠（見出し・規則の説明・3 ブロックの配置）と `GET /api/alerts/date-reversal`（A13）の `risks[]` 部分。
- [1] 見出しと副題（規則：同一顧客×SKU の納品済みロットより期限の早いロットを出荷しようとしている。本日日付とは比較しない、他顧客の履歴は借用しない）。
- [2] US-02 の説明ボックス（例：CUS-003 が CHI-002 の期限 X を受領済み → 期限が X より早い CHI-002 は CUS-003 への出荷時にブロック。例外は起票者 ≠ 承認者）。
- [3] 「ブロックされる出荷予定」（件数）：出荷待ちオーダーの行のうち、⑤ のロットが 1 件以上あり、かつ行状態が `date_reversal`（`severity='blocked'`）のもの。列：オーダー／出荷日、顧客、SKU／数量（「有効ロット {shortfall} 不足」赤、申請中なら「承認待ち」紫）、顧客への納品済み基準（ロット番号・期限）、在庫中の期限が早いロット（ロット・期限・在庫）、「処理 →」（`/outbound/{id}`）。
- [4] 「代替ロットで回避済み」（件数）：⑤ のロットが在庫にあるが FEFO 候補で必要数を満たせる行（`severity='avoided'`）。0 件なら非表示。
- 空状態：[3]「ブロック予定のオーダーはありません。」
- [ASSUMPTION] ブロック [5]（承認待ち一覧）と [6]（例外ログ）を配置する領域の確保までを本ストーリーで行い、中身は E-06-S02 / E-06-S03 が実装する。
- ダッシュボードのカード「日付逆転でブロック中の行」（E-08-S01）からの遷移先。

**対象外**

- 例外申請・承認パネルと承認待ち一覧（E-06-S02）。
- 不変の例外ログの表示・絞込・CSV 出力（E-06-S03）。
- メール通知（IF-MAIL-01、E-12-S02）。
- 日付逆転判定ロジック本体（E-05-S02）。

## 6. 主要業務フロー

**正常フロー**

1. 管理者がメニューまたはダッシュボードのカードから `/alerts` を開く。
2. 画面が `GET /api/alerts/date-reversal` を呼ぶ。BFF は全出荷待ちオーダーに共通エンジン（ピッキング計画）を実行し、⑤ のロットを持つ行を `blocked` / `avoided` に分類する。
3. [3] に OUT-261003-03（CUS-003 / CHI-002 × 24、基準 LOT-CHI002-C、早いロット LOT-CHI002-A・LOT-CHI002-B）が表示される。
4. 管理者は「処理 →」で引当画面を開き、担当作業者に別ロットの確保を指示するか、営業に顧客の書面同意の取得を依頼して例外申請（E-06-S02）へ進める。
5. 該当行が出荷済みになる、または代替ロットが入荷すると、次回表示時に [3] から消える（または [4] に移る）。

**代替・例外フロー**

- ブロック予定なし：[3] に空状態を表示、[4] は非表示。
- 申請中のオーダー：[3] の該当行に「承認待ち」を表示（ブロック対象として残す）。
- CUS-005 宛て CHI-002（OUT-261004-05）：⑤ がないため [3]・[4] のどちらにも出ない。
- 未ログイン 401（ログイン画面へ）、ロール未付与 403、DB 接続不可 503（再試行ボタン）。
- API エラー時は共通ルールどおり赤枠と「再試行」。
- [ASSUMPTION] [3] / [4] の並び順は出荷日昇順、同日はオーダー番号順（出荷が近いものから対応するため）。

## 8. 技術的制約・非機能面の考慮

- 判定は E-05-S02 の TS エンジン（二層判定の第一層、ADR-003）。最終防衛線は SQL の `DATE_REVERSAL`。
- NFR-PERF-01：p95 読取 ≤ 2 秒。全出荷待ちオーダーのピッキング計画を毎回算出する（出荷待ちは少数の想定）。出荷待ちが数百件を超える場合は短時間キャッシュを追加する（画面仕様 §10）。
- NFR-SEC-02：閲覧は全ロール（RLS）。書込はない。
- NFR-LOC-01：日本語・JST。NFR-ACC-01：重要度は色と文言の両方で示す。
- ADR-002：ブラウザから DB を直接呼ばない。ADR-006：ローカル Supabase で開発・テスト。

## 9. 受入基準

- [ ] Given シード（R-06）、When manager が `/alerts` を開く、Then [3] に OUT-261003-03 / CUS-003 / CHI-002 が 1 件表示され、基準 LOT-CHI002-C と早いロット LOT-CHI002-A・B（期限・在庫付き）が並ぶ。（E2E）
- [ ] CUS-005 / CHI-002（OUT-261004-05）と CUS-004 の行は [3]・[4] に表示されない（他顧客の履歴を借用しない）。（E2E＋ユニット）
- [ ] 期限が基準と同日のロットしかない行は表示されない。判定に本日日付を使っていない（基準のない SKU は対象外）。（ユニット）
- [ ] ⑤ のロットはあるが FEFO 候補で足りる行は [4] に表示され、[3] には表示されない。[4] が 0 件ならブロック自体が非表示。（ユニット＋E2E）
- [ ] 例外申請中のオーダーの行に「承認待ち」バッジが表示される。（E2E）
- [ ] [3] の件数が、ダッシュボードの「日付逆転でブロック中の行」と一覧（SCR-12）の「日付逆転で停止」合計と一致する。（統合テスト）
- [ ] 「処理 →」で `/outbound/{id}` に遷移する。warehouse・sales・auditor でも閲覧できる。（E2E）
- [ ] 未ログイン 401、ロール未付与 403。（統合テスト）
- [ ] DoD D-003（顧客×SKU 単位の日付逆転、ACC-DATE-01）と D-001（SCR-05）の証跡を残す。
